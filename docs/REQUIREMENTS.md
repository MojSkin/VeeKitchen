## ۱. معرفی پروژه

**نام پروژه:** VeeKitchen
**نوع:** نرم‌افزار مدیریت رستوران (Restaurant Management System) — **چندشعبه‌ای/SaaS از همان ابتدا**
**پلتفرم هدف:** وب — SPA + PWA، Mobile-First، تجربه‌ی کامل روی دسکتاپ
**زبان/جهت:** فارسی، کاملاً RTL
**واحد پول:** تنها **تومان** — بدون پشتیبانی چندارزی
**محل توسعه:** `D:\Projects\VeeKitchen` — باید در **Claude Code** یا ترمینال محلی ساخته شود (نه در یک چت‌بات معمولی)

### کاربران سیستم (Actors)
- **مدیر/مالک رستوران** — دسترسی کامل، تنظیمات، گزارش‌های مالی، مدیریت چندشعبه‌ای
- **صندوق‌دار (Cashier)** — دریافت وجه، چاپ فیش، تسویه روزانه، صدازدن مجدد شماره
- **آشپز/کارکنان آشپزخانه (Kitchen Staff)** — مشاهده و مدیریت صف آماده‌سازی
- **گارسون (Waiter)** — *نقش جدا یا نه، هنوز تصمیم‌گیری نشده؛ enum نقش‌ها باید طوری طراحی شود که افزودن این نقش بعداً فقط یک enum value جدید باشد، نه تغییر ساختاری*
- **مشتری (Customer)** — مهمان (بدون ثبت‌نام) یا عضو (با پروفایل)

## ۲. Tech Stack (نهایی و ثابت)

| لایه | تکنولوژی |
|---|---|
| Backend | Laravel (آخرین نسخه پایدار) |
| Frontend | Vue 3 (Composition API) |
| پل Backend↔Frontend | Inertia.js (بدون REST API جدا برای صفحات؛ برای موبایل/PWA آفلاین در صورت نیاز از API جدا هم استفاده می‌شود) |
| استایل | Tailwind CSS |
| دیتابیس | **MySQL** (پروداکشن) — توسعه/تست روی sqlite؛ مایگریشن‌ها سازگار با هر دو موتور |
| Real-time | Laravel Reverb (سرور WebSocket) + Laravel Echo (کلاینت) |
| Push Notification | Web Push (VAPID) — پیاده‌سازی رایگان، بدون سرویس ابری پولی |
| TTS (اعلام صوتی) | **Web Speech API مرورگر** (سمت کلاینت، رایگان، بدون سرویس ابری) |
| OCR منو از عکس | ❌ **حذف شده از اسکوپ** — منو فقط به‌صورت دستی وارد می‌شود (PHP توانایی OCR داخلی ندارد و استفاده از سرویس ابری پولی رد شد) |
| نوع اپ | SPA + PWA (قابل نصب، آیکون، Service Worker، آفلاین محدود) |
| طراحی | Mobile-First / Mobile-Friendly، دسکتاپ = امکانات کامل، موبایل = حس اپ نیتیو |

### پورت‌بندی (به‌روزرسانی ۱۴۰۵/۰۷ — جایگزین تصمیم شماره ۸ بخش ۷)
| سرویس | پورت |
|---|---|
| Laravel HTTP Server (`php artisan serve`) | `8020` |
| Laravel Reverb (WebSocket) | `8080` |
| Vite Dev Server (npm) | `8120` |

> تاریخچه: تصمیم اولیه 8008/8080/5180 بود؛ در هم‌ترازسازی با وضعیت مخزن و درخواست کارفرما، Laravel به 8020 و Vite به 8120 (با فاصله ۱۰۰) منتقل شد و Reverb روی پیش‌فرض سند (8080) ماند.

> سند علت دیتابیس: **sqlite برای توسعه/تست، MySQL برای پروداکشن.** همه مایگریشن‌ها باید با هر دو موتور سازگار بمانند.

این مقادیر باید در `.env` به‌صورت متغیر (`APP_PORT`, `REVERB_PORT`, `VITE_PORT` و ...) تعریف شوند تا در آینده قابل تغییر باشند.

### ⚠️ نکته فنی: iOS Web Push
Web Push روی iOS Safari فقط زمانی کار می‌کند که PWA به Home Screen اضافه شده باشد؛ برای مشتری‌ای که فقط در تب مرورگر سفارش می‌دهد و PWA را نصب نکرده، روی آیفون Push دریافت نمی‌شود (فقط Echo هنگام باز بودن تب کار می‌کند). UI باید مشتری را به نصب PWA تشویق کند.

### ⚠️ نکته فنی: پرینتر فیش
- **پرینتر شبکه‌ای (IP):** بک‌اند لاراول مستقیم روی سوکت TCP دستورات ESC/POS ارسال می‌کند — بدون نیاز به نرم‌افزار اضافه.
- **پرینتر USB:** مرورگر دسترسی مستقیم ندارد؛ نیاز به یک ایجنت محلی (مثل QZ Tray) روی سیستم صندوق است.
- **هر دو حالت باید پشتیبانی شود** — در تنظیمات هر صندوق/شعبه یک فیلد «نوع اتصال پرینتر» (USB / Network) قرار می‌گیرد.

## ۳. ماژول‌های اصلی

### ۳.۱ مدیریت منو (Menu Management)
- CRUD کامل برای دسته‌بندی، محصول، قیمت، تصویر، توضیحات، وضعیت موجود/ناموجود
- ورود منو **کاملاً دستی** (بدون OCR/AI Vision)

### ۳.۲ آنالیز متریال محصول (Product ↔ Material)
- هر محصول می‌تواند به یک یا چند «متریال/ماده اولیه» (Inventory Item) مرتبط شود
- هر متریال دارای واحد اندازه‌گیری (کیلوگرم، گرم، لیتر، عدد و ...)، موجودی فعلی، حداقل موجودی هشدار (Low Stock Alert)
- **برچسب بارکد/QR برای هر متریال انبار** (تایید شده برای v1) — برای ردیابی سریع‌تر فیزیکی موجودی

### ۳.۳ فرمول تولید (Recipe / BOM — Bill of Materials)
- هر محصول یک «فرمول تولید» دارد: لیستی از متریال‌ها + مقدار مصرفی هرکدام برای تولید یک واحد محصول
- هنگام فروش/تولید یک محصول → به‌صورت خودکار مقدار متریال مصرفی از انبار **کسر** می‌شود
- **اجزای هزینه (Cost Components):** فرمول باید امکان افزودن اجزای نامحدود و دلخواه داشته باشد؛ هرکدام با نوع (درصدی یا مبلغ ثابت) و ترتیب اعمال (مالیات، سود مدیریت، سربار، بسته‌بندی، عوارض و...)
- خروجی نهایی: **قیمت تمام‌شده (Cost Price)** و **قیمت فروش پیشنهادی (Suggested Sale Price)** — با اعمال قانون رند (بخش ۵) محاسبه می‌شود
- تاریخچه‌ی تغییرات فرمول باید نگه‌داشته شود

### ۳.۴ سیستم مالی و حسابداری (Financial System)
- ثبت خودکار هر تراکنش فروش، بازگشت وجه/کنسلی، هزینه‌های جانبی
- گزارش سود/زیان، گزارش فروش روزانه/هفتگی/ماهانه
- **تسویه روزانه صندوق (Daily Cash Reconciliation):** موجودی اولیه، شمارش پایان شیفت، ثبت مغایرت، چاپ/ذخیره گزارش
- امکان کنسل کردن سفارش (با ثبت دلیل) و اثر آن روی گزارش مالی و بازگشت متریال به انبار
- **پرداخت:** فقط حضوری (نقد/کارت‌خوان فیزیکی) در نسخه فعلی؛ مدل `Payment` باید از همین ابتدا با فیلدهایی مثل `method` و `gateway_reference` طراحی شود تا افزودن درگاه آنلاین در آینده نیاز به بازسازی نداشته باشد

### ۳.۵ نمایش منو روی مانیتور (Digital Signage)
- صفحه‌ی مخصوص بدون لاگین برای پخش روی تلویزیون/مانیتور، به‌روزرسانی real-time هنگام تغییر قیمت/موجودی

### ۳.۶ میزها و QR Code
- تعریف میز با شماره/نام + ظرفیت، QR Code یکتا (توکن امن، غیرقابل‌حدس)
- اسکن QR → رزرو میز → نمایش منو مختص همان میز
- آزادسازی دستی میز توسط مدیر/صندوق‌دار
- وضعیت میز: آزاد / رزروشده / در حال سفارش / منتظر تسویه
- **صف انتظار میز (Waitlist)** تایید شده برای v1 — وقتی همه میزها پرند

### ۳.۷ فرآیند سفارش مشتری
۱. مشتری منو را می‌بیند و سفارش را در سبد خرید ثبت می‌کند
۲. سفارش ثبت‌شده → «منتظر پرداخت» → آنی به صندوق ارسال می‌شود
۳. مشتری حضوراً در صندوق مبلغ را پرداخت می‌کند
۴. صندوق‌دار پرداخت را تایید می‌کند → شماره سفارش تعلق می‌گیرد و فیش چاپ می‌شود
۵. شماره سفارش قابل ریست توسط مدیر (مثلاً شروع مجدد از ۱ در ابتدای هر روز)
۶. سفارش وارد صف آماده‌سازی آشپزخانه می‌شود
- **تقسیم صورت‌حساب (Split Bill)** تایید شده برای v1 — تقسیم هزینه بین چند نفر روی یک میز

### ۳.۸ وضعیت‌های سفارش
```
منتظر پرداخت → در صف آماده‌سازی → آماده تحویل → تحویل شده
                                              ↘ کنسل‌شده (در هر مرحله با مجوز مدیر/صندوق)
```

### ۳.۹ Real-time و اطلاع‌رسانی (Reverb + Echo + Web Push)
- آشپزخانه: سفارش جدید پرداخت‌شده → بلادرنگ روی KDS
- مشتری: تغییر وضعیت سفارش → هم Echo (تب باز) و هم Web Push (حتی تب/اپ بسته) به‌صورت هم‌زمان (Redundancy) — با توجه به محدودیت iOS در بخش ۲
- صندوق/مدیر: اعلان سفارش جدید، درخواست کنسل، هشدار موجودی کم
- کانال‌های پیشنهادی: `table.{id}`, `order.{id}`, `kitchen-queue`, `admin-notifications`

### ۳.۱۰ پروفایل مشتری (اختیاری)
- خرید بدون ثبت‌نام (Guest Checkout) امکان‌پذیر است
- ثبت‌نام اختیاری → مشاهده تاریخچه سفارش‌ها
- طراحی دیتابیس باید از همین ابتدا آماده‌ی افزودن راحت Cashback و Loyalty در آینده باشد

### ۳.۱۱ سیستم تخفیفات
- کد تخفیف با: درصدی/مبلغ ثابت، تاریخ شروع/انقضا، سقف کلی، سقف به‌ازای هر کاربر
- تخفیف بر اساس: کل سبد، دسته‌بندی خاص، محصول خاص، حداقل مبلغ سفارش
- تخفیف خودکار (بدون کد) — مثلاً اولین خرید عضو، ساعات خلوت
- طراحی توسعه‌پذیر برای تخفیف پلکانی/ترکیبی در آینده

### ۳.۱۲ صف آشپزخانه (KDS)
- نمایش سفارشات پرداخت‌شده به ترتیب اولویت/زمان
- علامت‌گذاری «در حال آماده‌سازی» → «آماده» → فراخوانی TTS و انتقال به صف «آماده تحویل»

### ۳.۱۳ اعلام صوتی شماره سفارش (TTS)
- زبان فارسی، صدای زن/مرد قابل انتخاب توسط مدیر — از طریق **Web Speech API مرورگر** (رایگان)
- سفارش میز: «شماره [X] میز [Y]» / سفارش مستقیم: «شماره [X]»
- دکمه «تکرار اعلان» برای مدیر/صندوق‌دار
- نمایش ساده و بزرگ صف «آماده تحویل» مناسب مانیتور کنار صندوق

### ۳.۱۴ امتیازدهی و نظر مشتری
- بعد از تحویل، امتیاز (۱ تا ۵) و نظر متنی برای هر آیتم
- مدیریت/تایید نمایش عمومی نظرات در پنل مدیر

### ۳.۱۵ داشبورد مدیریتی
- KPIها: فروش امروز/بازه، پرفروش‌ترین محصولات، وضعیت میزها زنده، هشدار موجودی، وضعیت صندوق — به تفکیک شعبه
- گزارش‌های مالی/تولید قابل خروجی Excel/PDF
- **گزارش خودکار پایان روز** تایید شده برای v1 — خروجی PDF/Excel شامل فروش، تسویه صندوق، مصرف انبار، ارسال شبانه به مدیر (Email/Push)

### ۳.۱۶ تم روشن/تاریک
- تشخیص خودکار `prefers-color-scheme` + امکان تغییر دستی و ذخیره در پروفایل/local storage

### ۳.۱۷ مدیریت تامین‌کننده و سفارش خرید (تایید شده برای v1)
- هشدار موجودی کم + ثبت سفارش خرید از تامین‌کننده

### ۳.۱۸ ردیابی ضایعات و تاریخ انقضا (تایید شده برای v1)
- جدا از مصرف تولیدی، برای گزارش دقیق سود واقعی

### ۳.۱۹ مدیریت شیفت کارکنان (تایید شده برای v1)
- ثبت ورود/خروج شیفت آشپز و صندوق‌دار، اتصال به گزارش تسویه صندوق

### ۳.۲۰ حالت مقاومت آفلاین صندوق (تایید شده برای v1)
- در صورت قطعی موقت اینترنت، ثبت محلی و همگام‌سازی بعدی

### ۳.۲۱ لاگ ممیزی مالی/انبار (تایید شده برای v1)
- ثبت این‌که چه کاربری چه تغییری و چه زمانی داده

### ۳.۲۲ لینک/QR عمومی منوی دیجیتال (تایید شده برای v1)
- مستقل از میز، برای اشتراک در شبکه‌های اجتماعی یا نمایش قبل از ورود

## ۵. الزامات غیرعملکردی (Non-Functional Requirements)

- **Mobile-First:** طراحی از موبایل شروع، سپس گسترش برای دسکتاپ
- **PWA:** قابل نصب، آیکون و splash screen اختصاصی، Service Worker برای کش استاتیک و Web Push
- **امنیت سفارش مهمان:** توکن QR هر میز امضاشده/غیرقابل‌حدس؛ Rate Limit روی ثبت سفارش
- **RTL و زبان فارسی:** رابط کاربری کاملاً راست‌به‌چپ و فارسی
- **Real-time reliability:** استفاده هم‌زمان از Reverb و Web Push برای مشتری (Redundancy)
- **چندشعبه‌ای:** تمام موجودیت‌های اصلی باید `branch_id` داشته باشند؛ گزارش‌ها و داشبورد باید قابل فیلتر به تفکیک شعبه یا تجمیع کل شعب باشند
- **قانون رند مالی:** واحد پول فقط تومان است. تمام مبالغ نهایی محاسبه‌شده (قیمت تمام‌شده، قیمت فروش پیشنهادی، جمع نهایی سفارش بعد از تخفیف) باید **رو به بالا (Ceiling)** به نزدیک‌ترین ۱۰۰ تومان گرد شوند — هیچ مبلغی زیر ۱۰۰ تومان مجاز نیست
- **مقیاس‌پذیری آینده:** طراحی باید افزودن Cashback، Loyalty، و نقش گارسون را بدون بازنویسی اساسی ممکن کند

## ۶. جریان‌های کاری کلیدی (User Flows) — خلاصه

**مشتری روی میز:**
اسکن QR → رزرو میز → مشاهده منو → افزودن به سبد → ثبت سفارش (منتظر پرداخت) → مراجعه به صندوق → پرداخت → دریافت فیش با شماره → پیگیری وضعیت (Real-time) → دریافت اعلان «آماده تحویل» (صدا + Push) → دریافت سفارش → (اختیاری) ثبت نظر/امتیاز

**آشپز:**
ورود به KDS → مشاهده سفارش جدید (Real-time) → «در حال آماده‌سازی» → «آماده» → اعلام صوتی خودکار + به‌روزرسانی صف تحویل

**مدیر:**
ورود به داشبورد → مشاهده KPIها (به تفکیک/تجمیع شعب) → مدیریت منو → مدیریت فرمول تولید و انبار → بررسی گزارش مالی → تسویه/بستن صندوق پایان روز
